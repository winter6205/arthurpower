# issue-triage-validator

## When to use

- 外部 issue 流到达，需要分拣
- 收到外部 PR 或 inbound support item
- 待处理项标记为 unclassified、needs-triage 或 lacks enough information
- 必须 assign category role + state role + owner-ready brief 的工作项
- 在路由到实施 agent 之前需要 verify claim（复现 bug 或 checkout PR 跑测试）

## When not to use

- 待处理项已被正确分类且已有活跃实现 cycle
- 纯文档修正，无行为 claim 需要 verify
- 超出单一可复现 claim 范围，需开放调试 → 路由到 `systematic-debugging`
- 需深度领域建模 → 路由到 `domain-modeling`
- 需对抗性盘问 proposal → 路由到 `deep-dive-protocol`

## Procedure

### 1. 扫描待处理队列

查询 request tracker 或 inbox，筛选：
- `unclassified`
- `needs-triage`
- `needs-info`

按 oldest first 排序，输出编号列表（标题 + 时长 + 当前标签）。

### 2. 收集上下文

对所选 item 收集：
- 原始标题与 body
- 作者、关联 PR、关联 commit、关联讨论
- 已有标签、milestones、prior state changes
- 关联测试、关联源文件、关联文档

### 3. 冗余检查 + prior-rejection 检查

- 搜索重复标题或近重复 body
- 检查 `.out-of-scope/` 或 prior `wontfix` 记录
- 如为 duplicate，路由到 state `duplicate` 并引用原条

### 4. 验证 claim

对所选 item 执行最低限定验证：

| 类型 | 验证方法 |
|------|----------|
| bug report | 按步骤复现，或要求 reporter 提供最小复现步骤 |
| external PR | checkout 分支，跑相关测试套件 |
| enhancement request | 确认功能与项目范围和现有路线图对齐 |
| 无法完成验证 | assign state `needs-info`，列出确切缺失信息 |

### 5. 应用 category + state 角色

Category 角色（三选一）：
- `bug`
- `enhancement`
- `maintenance`
- `out-of-scope`

State 角色（五选一）：
- `needs-info`
- `ready-for-agent`
- `ready-for-human`
- `wontfix`
- `duplicate`

### 6. 输出 triage brief

含以下字段：
- 当前 state
- 谁能接（agent role 或 human role）
- 怎么接（next action + 推荐 skill）
- disclaimer：该 triage 决定为临时性，subject to human review

## External PR path

### Principle: a PR is an issue with attached code

Treat every external PR exactly as if it were an issue, plus the attached diff. The 5-state machine is preserved without renaming:

- `needs-info` — waiting on reporter / contributor for more information
- `ready-for-agent` — fully specified, ready for an AFK agent
- `ready-for-human` — needs human implementation
- `wontfix` — will not be actioned
- `duplicate` — duplicates a prior triaged item

For a PR, the states read against the attached code:

- `ready-for-agent` means an AGENT-BRIEF is attached and an agent should take the next step on the diff (finish it, close gaps, address review points).
- `ready-for-human` means the diff is ready for a human to merge (judgment calls, external access, design decisions, manual testing remain).

### Read-first rule

Before triaging an external PR, READ the diff to verify the claimed gap against the current repository state. Run the relevant tests, check the touched interfaces, and confirm whether the requested behavior is already implemented.

- If the repo already covers the gap (already-implemented): add only the `[PR]` line marker and the AI-during-triage disclaimer; do **not** fabricate work or write an AGENT-BRIEF.
- If the gap is real: proceed with the standard Procedure (redundancy, prior rejection, verification, grilling, brief).

### Tagging: `[PR]` / `[issue]`

Every triaged line in the discovery buckets and every auto-posted comment must carry a `[PR]` or `[issue]` line marker. Discovery surfaces only **external** PRs — a collaborator's in-flight PR is not triage work and stays out of the unattended bucket. An explicitly named PR (e.g. "triage #42") is always triaged regardless of author.

### AI-during-triage disclaimer prefix

Every comment, brief, or triage note auto-posted to an external PR or issue during triage **must** start with this disclaimer prefix (reuses the project-wide AI-triage disclaimer; the triage decision is provisional, subject to human review):

> *This triage decision was generated by AI during triage and is provisional, subject to human review.*

The disclaimer precedes the AGENT-BRIEF or Triage Notes body. It does not replace the maintainer's confirmation; the final state assignment still needs human ratification.

### AGENT-BRIEF comment template

When an external PR moves to `ready-for-agent`, post an Agent Brief as a PR comment. The brief is the contract an AFK agent will work from; the PR body and discussion are context. For a PR, "Current behavior" describes the state of the diff, and the brief asks the agent to finish or fix the diff rather than build from scratch.

```markdown
> *This triage decision was generated by AI during triage and is provisional, subject to human review.*

## Agent Brief

**Category:** bug / enhancement
**Summary:** one-line description of what needs to happen

**Current behavior:**
Describe what happens now, or — for a PR — the current state of the diff
(gaps, unfinished pieces, review points).

**Desired behavior:**
Describe what should happen after the agent's work is complete.
Be specific about edge cases and error conditions.

**Key interfaces:**
- `TypeName` — what needs to change and why
- `functionName()` return type — what it currently returns vs what it should return
- Config shape — any new configuration options needed

**Acceptance criteria:**
- [ ] Specific, testable criterion 1
- [ ] Specific, testable criterion 2
- [ ] Specific, testable criterion 3

**Out of scope:**
- Thing that should NOT be changed or addressed in this PR
- Adjacent feature that might seem related but is separate
```

#### Durability principles (apply when writing the brief)

These principles keep a brief useful even as the codebase moves. The agent will explore fresh and make its own implementation choices, so the brief must be both durable and behavioral.

- **Durability over precision** — describe interfaces, types, and behavioral contracts; do **not** reference file paths or line numbers (they go stale across refactors).
- **Behavioral, not procedural** — describe *what* the system should do, not *how* to implement it.
- **Complete acceptance criteria** — every brief carries concrete, testable criteria; each criterion is independently verifiable.
- **Explicit scope boundaries** — state out-of-scope items to prevent gold-plating or assumption-driven expansion.
- **Category discipline** — for an external PR, the brief belongs to one of the existing categories: `bug` (something is broken) or `enhancement` (new feature / improvement). State this category role explicitly.

### Per-state behavior for an external PR

| State | Read-the-diff check | What gets posted |
|-------|---------------------|------------------|
| `needs-info` | Diff ambiguity or missing repro | Triage Notes block, no AGENT-BRIEF |
| `ready-for-agent` | Diff is verified, gap is real, brief attaches cleanly | Agent Brief (template above) |
| `ready-for-human` | Diff is ready to merge; judgment calls remain | Same structure as Agent Brief, plus a one-line note on why it cannot be delegated |
| `wontfix` | Diff is rejected | Single-line close + rationale + (if enhancement) `.out-of-scope/` entry pointer; do **not** fabricate work |
| `duplicate` | Diff duplicates a prior triaged PR/issue | Close with reference to the original item's URL/state |

### Acceptance for the external-PR path

- [ ] Every triaged line carries a `[PR]` or `[issue]` marker.
- [ ] Every auto-posted comment starts with the AI-during-triage disclaimer.
- [ ] `ready-for-agent` is accompanied by an AGENT-BRIEF comment (template above), with durability principles applied (no file paths / line numbers).
- [ ] Category role is one of `bug` / `enhancement`; state role is one of the 5 preserved states.
- [ ] If the repo already covers the gap, only the `[PR]` marker + disclaimer are posted (no fabricated AGENT-BRIEF).
- [ ] Discovery only surfaces external PRs; an explicitly named PR is always triaged.

## Acceptance Criteria

- [ ] 每个 item 被分配恰好一个 category + 一个 state
- [ ] 验证已执行，或明确 defer 并标记 `needs-info`
- [ ] brief 含 state、owner、next action
- [ ] brief 含 disclaimer
- [ ] 没有 item 被静默丢弃

### Rationalization Table

| Pressure | Why it sounds right | Counter-evidence | Required action |
|----------|---------------------|------------------|-----------------|
| Triage volume is high | Speed matters more than accuracy | A wrong triage wastes a human's time to reclassify | Process the full checklist, not a subset |
| The claim looks obviously true | The title alone is enough to route | Title mismatches body content in 1/4 of real issues | Always run Step 4 verification |
| External PRs are small enough to skip review | A PR is a contribution, not a threat | Malicious PRs hide in small diffs | Run the PR's tests and check out-of-scope first |
| The reporter is a trusted contributor | Their issue should get priority routing | Trusted contributors also file duplicates and false enhancement requests | Apply the same triage checklist regardless of origin |
| A `wontfix` decision seems obvious | The rationale is self-evident | Future contributors may reopen without understanding why | Cite the specific out-of-scope rule or prior ADR |

### Red Flags — STOP

- 跳过 bug 复现因为描述 "看起来明显"
- 在输出 brief 之前就编辑 tracker labels
- 路由到 `ready-for-agent` 未确认 item 可复现或在 scope 内
- 省略 disclaimer 让决策看起来不可撤销
- 把 duplicate 当作已解决，未引用原条目
- 未跑 `.out-of-scope/` 检查直接 close
- 一次 check-in 给多个未关联 item 分配同一个 state（批量 triage shortcut）
