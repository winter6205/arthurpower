## 3. 11 skill 制作思路

### 3.1 S1: bounded-context-guardian (Parnas 1972 限界上下文)

**设计意图**: 防止按技术层 (controllers/services/repositories) 切片, 强制按业务能力 (orders/billing/inventory) 切片. 解决"改 1 个 feature 改 N 个目录的 1 个 file" shotgun surgery 温床.

**关键决策**:
- 二元判据 (top-level dir 命名 / 跨 context interface / 无 cycle import / context map 存在) — 不容灰色
- 5 个反模式具体化 (controllers/services/repositories 散 / 跨 context 直接 import / models 顶层 / 改业务名跨 3+ 目录 / 重构信号)
- 重构信号: 改 1 feature = 改 N 目录的 1 file / 新人 PR 跨目录跳转 5+ 次 / context map 缺失

**适用场景**: 任何新项目 / 老项目重构 / code review 审 module boundary.

**参考**: 原创 (V 6/26 立, 基于 Parnas 1972 CACM "On the Criteria to Be Used in Decomposing Systems into Modules" + C4 Model + DDD Bounded Contexts).

---

### 3.2 S2: defensive-contract-validator (5-class boundary test)

**设计意图**: public function 必含 5 类边界测试 (empty / negative / long / concurrent / exception), 覆盖率阈值 line ≥ 80% + branch ≥ 70%. 解决"happy path only" 测试通过但 production crash.

**关键决策**:
- 5 类边界 (empty / negative / long / concurrent / exception) — 必全, 不容"测试太慢跳过"
- 并发测试允许 `// N/A: pure` 转义, 但转义条件严格 (referentially transparent + no module state closure)
- 防御契约 = test 本身 + coverage threshold, 不是"测试存在即合规"
- 与 minimal-change-verifier 协同: 5-class boundary test 必在 1 commit 内 (不拆 follow-up)

**适用场景**: 任何 public function / API endpoint / library function.

**参考**: 原创 (V 6/26 立, 基于 Kent Beck TDD + Robert C. Martin SRP + 80/70 coverage threshold).

---

### 3.3 S3: error-handling-enforcer (typed exception + Result + // EXIT:)

**设计意图**: 禁止空 catch / null/-1 返回 / untagged generic throw, 强制 typed exception per failure mode + Result<T, E> + // EXIT: comment. 解决"看似处理错误实际吞掉" 反模式.

**关键决策**:
- typed exception per failure mode (1 failure mode = 1 exception class, NOT 1 god-class)
- Result<T, E> 显式错误返回 (Rust / Python `returns` lib / Go `(T, error)` / Java sealed union)
- // EXIT: comment 每个 fallback / early-return 标出 caller 决策条件
- 主函数只描述 happy path, 错误处理在边界/出口集中 (fail-fast 原则)

**适用场景**: 任何 I/O + 解析 + 校验 function / 任何 try/catch / 任何 return null/-1.

**参考**: 原创 (V 6/26 立, 基于 Clean Code Ch.7 Error Handling + Code Complete Ch.8 Defensive Programming + Amazon Builders' Library "Avoiding Fallback in Distributed Systems").

---

### 3.4 S5: complexity-anti-drift (threshold + refactor pattern)

**设计意图**: 静态阈值 (function ≤ 30 lines / nesting ≤ 4 / file ≤ 300 lines / params ≤ 3 / clone ≤ 3%) + 5 个 refactor pattern (Extract Function / Inline / Move / Replace Conditional with Polymorphism / Introduce Parameter Object). 解决复杂度漂移 (一个分支 / 一个嵌套 / 一个参数, 每次添加本地合理全局致命).

**关键决策**:
- threshold 不可谈判 (4 params **exceeds** threshold, 不"再加点规则就好")
- 5 个 refactor pattern = 模式目录 (when + effort + 1-line example), 不是抽象指导
- 抽函数后必重测 linter (不"我加了 guard clause 就行")
- 抽函数后必 hand off 到 minimal-change-verifier (refactor + feat 拆 commit)

**适用场景**: 任何 > 30 line function / CI complexity gate failure / code review 审 threshold.

**参考**: 原创 (V 6/26 立, 基于 Clean Code Ch.3 Functions + Robert C. Martin SOLID + Refactoring 2nd ed. Ch.3 Bad Smells + ESLint complexity 规则).

---

### 3.5 S6: minimal-change-verifier (1 commit = 1 逻辑任务)

**设计意图**: 1 commit = 1 logical task (新增功能 / Bug fix / 格式调整 各 1 commit). 禁止 refactor + feat 混同 commit. 解决 1 commit 含多 task → revert 隔离失败 + git bisect 困难 + blame 混乱.

**关键决策**:
- 严词禁止 `refactor:` 与 `feat:` / `fix:` / `perf:` 同 commit
- 锁文件 iff dep 改变 (lockfile diff iff dep diff)
- pre-commit tests 必跑 (no `--no-verify`, no `.skip`)
- drive-by lint fix 单独 commit (muddy `git blame` / `git bisect`)
- 4 类 loophole 必封: `--amend` rewrite / `chore:` 前缀 / monorepo partial commit / "tests in next commit"

**适用场景**: 任何 commit 前 / PR 前 / 审 commit message / 审 lockfile 同步.

**参考**: 原创 (V 6/26 立, 基于 V 6/21 "1 commit = 1 逻辑任务" 字面 + commit-msg-refactor hook + git reflog + conventional commits).

---

### 3.6 ACR: architecture-change-reviewer (5-verdict pre-impl gate)

**设计意图**: multi-file change (3+ files 或 2+ Core Skill in scope) PR 前必走 5-verdict 框架 (S1-S6 各 1 行 verdict), 任一 no / unclear → 回对应 Core Skill 修 plan, 不进 Task Decomposition. 解决"multi-file change 凭感觉写, 改完发现违反 5 个规范之一".

**关键决策**:
- 5-line verdict block (S1-S6 各 1 行 yes/no/unclear + 1 句 reason)
- 任一 verdict = no → 必回 responsible Core Skill 修 plan, 不强写
- 2+ Core Skill 冲突 → sequence (split, then commit per split), 不 merge
- 5-verdict 全 yes → 才进 Task Decomposition (5-task template)
- Plan-Format Annex = 5-row table (verdict block / task decomposition / handoff sequence / PR description / sibling refs) load-bearing
- 与 writing-plans 协同: ACR 先, writing-plans 后 (5-verdict → ordered task list)

**适用场景**: 任何 multi-file change (3+ files) / new module / cross-module refactor / 2+ Core Skill in scope.

**参考**: 原创 (V 6/26 立, 基于 V 6/23 S1-S6 治理层 + Parnas 1972 设计决策封装 + Plan-Format Annex 自我包含).

### 3.7 skill-authoring (meta-skill, TDD-for-skills 7-step)

**设计意图**: 教 agent 如何写 skill. 7-step TDD-for-skills methodology: RED (写 baseline pressure scenario + 3 subagent 跑, document rationalizations verbatim) → GREEN (写 minimal skill address baseline violations) → REFACTOR (close loopholes, add Red Flags + Rationalization Table) → DEPLOY (V 字面 review before commit). 解决"agent 写 skill 凭印象, 没 baseline 验证, 漏洞百出".

**关键决策**:
- 7-step TDD-for-skills methodology (distilled from `legacy-governance-plugin:writing-skills` 22.6 KB → 5 KB + "Skill 通用化规则" 段)
- Skill 通用化规则 9 subsection (触发条件 / 通用规范形式 / 禁用字眼清单 / mapping 表 / 反模式 / 验证 / 例外 / 与 7-step 关系 / 与 self-evolving 关系) — going forward permanent
- 1 个 excellent example = deadline-pressure-skill (5-section body + Rationalization Table + Red Flags + Required Baseline + Verification, 完整可跑)
- 与 self-evolving 互为约束: self-evolving 禁自证权威 (verbatim / locked / 严守 / 一字不改 / 红线 / 必走 / 硬性), skill-authoring 禁 user 私有命名空间 (V 字面 / V 协作 / 等)
- 模仿非引用 (Round 9 改 5 处旧治理层 plugin 字眼): "Read legacy-governance-plugin:writing-skills" → "Apply 7-step methodology self-contained", methodology 内化在 §Procedure Step 1-7

**适用场景**: 写新 skill / 编辑现有 skill / 审 skill CSO + TDD-for-skills 合规.

**参考**: `legacy-governance-plugin:writing-skills` (22.6 KB) — 7-step TDD-for-skills methodology + CSO + Rationalization Table + Red Flags + Iron Law. **distilled, not copy** (Round 9 改 5 处旧治理层 plugin 字眼后完全 self-contained).

### 3.8 verification-before-completion (evidence before claims)

**设计意图**: 任何"完成"声称前必跑 actual test + capture output + 比对 criterion, 报告用 `成功 = <criterion> <evidence>` 格式. 解决"agent 凭印象说完成, 没 fresh test 验证".

**关键决策**:
- 6 步流程: 写 binary criterion → 跑 fresh test (not cached) → paste verbatim output → 比对 → mismatch 时 stop+fix+re-run → 报告用 `成功 = <criterion> <evidence>` 格式
- 严词禁用 "looks good" / "应该可以" / "估计" / "大概" / "似乎" (严词规范)
- 严禁: paraphrase 输出 / 跳过 test / "verify later" / 信任 subagent "success" 不独立 re-run
- Cross-references: 端到端实测 = 唯一真值 (通用 spec, 不绑 V 私有 L1)

**适用场景**: 任何"完成"声称 / commit 前 / push 前 / subagent 返回 "success" 后 / 任何 user-facing message 声称成功.

**参考**: `legacy-governance-plugin:verification-before-completion` (4.2 KB) — evidence before claims 原则. **distilled, not copy** (Round 6 去 V 私有化 + Round 8 改 wording, 完全自包含).

### 3.9 systematic-debugging (4-phase root cause)

**设计意图**: 任何 bug 必走 4-phase (REPRODUCE → ISOLATE → INSTRUMENT → FIX), 找 root cause ≠ symptom location. 解决"agent 凭印象打补丁, symptom fix 掩盖真因, 3+ fix 失败后还没 root cause".

**关键决策**:
- Iron Law: NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST + NO "FIXED" CLAIM WITHOUT FAILING TEST GOING GREEN
- Phase 1 REPRODUCE: 必 fail rate ≥ 90% 才能进 Phase 2 (flaky = 不可修)
- Phase 2 ISOLATE: `git bisect` + 找 root cause (symptom location ≠ 真因)
- Phase 3 INSTRUMENT: 最小 log/print 验证假设 (不"try this and see")
- Phase 4 FIX: minimum fix at root cause + re-run failing test + run full suite (new failure = wrong fix)
- 嵌入 V debug-stop 4 phases (3 attempts fail → reload / 2 max_turns → subagent-driven-development / sub-agent fail → dispatching-parallel-agents / 500+ lines → split)
- 1 个 excellent example = 4-phase 完整流程 (REPRODUCE flaky test → ISOLATE git bisect → INSTRUMENT log race condition → FIX per-thread DB session)

**适用场景**: 任何 test fail / build break / behavior 不符预期 / flaky test / 3+ fix 失败.

**参考**: `legacy-governance-plugin:systematic-debugging` (9.9 KB) — 4-phase reproduce/isolate/instrument/fix + 铁律 + pressure scenarios. **distilled, not copy** (Round 6 去 V 私有化 + Round 8 改 wording, 完全自包含).

### 3.10 writing-plans (Plan Format 模板)

**设计意图**: multi-step task 前必写 plan, 5 字段齐 (Goal / Architecture / Tech Stack / Spec link / Tasks) + Task Decomposition ordered by dependency + [parallel] markers + [blocks: T<n>] dependencies + 1 commit per task + binary acceptance criterion + Cross-references (ACR verdict + S1-S6 affected + parallelization surface). 解决"agent 凭直觉写 multi-file change, 改完发现 task 漏 / 顺序错 / acceptance 模糊".

**关键决策**:
- 5 字段必填 (Goal 1 句话 / Architecture 1-3 行 / Tech Stack 列具体版本 / Spec link 必填 / Tasks ordered by dependency)
- Acceptance = binary 命令 + exit code (不"基本完成" / "大致可用")
- Commit: 1 commit = this 1 task (per task 单独一句强制提醒, 禁止拆分再合并)
- [parallel] 标记真实 (改的文件完全不同 / 无共享 state / 无先后依赖, 满足 3 条才标)
- 与 ACR 协同: ACR 先 (5-verdict 框架), writing-plans 后 (5-verdict 全 yes 才进, ACR 失败时不写 plan, 回 §Procedure Step 3)

**适用场景**: 任何 multi-file change (3+ files) / new module / cross-module refactor / ambiguous scope.

**参考**: `legacy-governance-plugin:writing-plans` (6.1 KB) — multi-step plan before code 原则 + Plan Format. **distilled, not copy** (Round 6 去 V 私有化 + Round 8 改 wording, 完全自包含).

### 3.11 dispatching-parallel-agents (1 message N subagent parallel)

**设计意图**: 2+ 真正独立任务 (无共享 state / 文件 / config / in-flight 依赖) 必 1 message N Agent tool invokes parallel, 不串行 3 message = 假并行. 解决"agent 串行 dispatch 假并行, 浪费 context cost" + "subagent scope 漂移 / file conflict / 凭印象盲改".

**关键决策**:
- 6 步流程: 识别 2+ 真正独立任务 → 写 N 个 self-contained prompt (ROLE / SCOPE / PERMISSION / REFERENCE / CONSTRAINTS / DELIVERABLE / OUTPUT RULES 7 项必含) → 1 message N Agent invokes parallel → structured result (有 test exit code + output summary, 不"看起来好") → 主代理 cross-check (scope creep / file conflict / dependency violation / 协作规范) → 集成 (按 issue 拆 follow-up, 不直接 commit review 结果)
- subagent scope ≤ 1 file 或 1 逻辑任务, ≤ 500 行 (硬上限)
- 严词: 2+ subagent 改同一文件 = conflict 必发 / subagent scope > 500 行 = 违规 / subagent prompt 缺 PERMISSION = scope 漂移 / 主代理跳过 cross-check = 静默 conflict
- 1 个 excellent example = 1 message 3 subagent parallel review (Hero.vue / run.py / orders.py, 6 步完整流程)

**适用场景**: 2+ 真正独立 task (review / refactor / test) / context 爆炸 / 并行审查不同文件 / 独立探索陌生代码 / 批量修复 N 个同类 bug.

**参考**: `legacy-governance-plugin:dispatching-parallel-agents` (6.4 KB) + `legacy-governance-plugin:subagent-driven-development` (12.5 KB) — 合并自两者, **distilled, not copy** (Round 6 去 V 私有化 + Round 8 改 wording, 完全自包含).

## §6 Skill 体系依赖图 (轻量版)

### 触发层级

```
Layer 0 — 元技能 (写 skill 时用)
  └── skill-authoring

Layer 1 — 核心治理 (每次代码变更必查)
  ├── S1 bounded-context-guardian     (模块边界)
  ├── S2 defensive-contract-validator  (5 类边界测试)
  ├── S3 error-handling-enforcer       (typed exception)
  ├── S4 complexity-anti-drift         (阈值 + 重构)
  └── S5 minimal-change-verifier       (1 commit = 1 任务)

Layer 2 — 流程门控 (3+ 文件变更时触发)
  ├── architecture-change-reviewer     (5-verdict 预审, 调度 S1-S5)
  ├── writing-plans                    (任务分解)
  ├── verification-before-completion   (完成前验证)
  └── systematic-debugging             (4-phase 调试)

Layer 3 — 调度 (2+ 独立任务时触发)
  └── dispatching-parallel-agents      (子代理编排)
```

### 加载顺序

1. **简单任务** (单文件 typo fix): 不加载任何 skill
2. **常规任务** (1-2 文件): Layer 1 按需加载相关 S1-S5
3. **复杂任务** (3+ 文件): Layer 2 先跑 architecture-change-reviewer → writing-plans → 执行 → verification-before-completion
4. **并行任务** (2+ 独立): Layer 3 dispatching-parallel-agents 编排
5. **写新 skill**: Layer 0 skill-authoring

### 协作关系

- **architecture-change-reviewer** 是调度器，输出 5-verdict 后指向 S1-S5 具体执行
- **systematic-debugging** 失败时可联动 dispatching-parallel-agents 拆分子任务
- **verification-before-completion** 是所有 Layer 2 skill 的出口门控
- **skill-authoring** 独立于运行链路，仅在创建/编辑 skill 时加载
