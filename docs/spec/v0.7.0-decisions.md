## 2. 5 轮裁决详记 (前 5 轮, 围绕 user/model 分类)

### 第 1 轮: auto-trigger 真实性

**真实场景**:
- A. 新 session "继续上次的工作" -> using-agent-skills description 含 "starting a new session / switching tasks", 是 model 自己识别. 强制 user 破坏 router 价值.
- B. "我要重构跨 3 个文件" -> writing-plans ("even if they don't say 'plan'") 和 ACR ("3+ files before implementation") 同时触发.
- C. "这个 bug 怎么修" -> systematic-debugging model auto-reach, 正确.

**修正**: using-agent-skills -> model (撤回 C "router 概念归 user" 误判). writing-plans -> model (第 1 轮判断, 第 3 轮撤回).

**好的保留**: skill-authoring 维持 user (reference skill, flat vocabulary, 跟 the baseline writing-great-skills 一致).

### 第 2 轮: gate 语义

**真实场景**:
- D. "把我刚才那个 commit 撤了" -> commit-revert-protocol. 用户已明确要撤, 但 "撤了" 可能是 working tree / commit / push 三种级别. **撤销级别歧义**需 human 确认.
- E. "帮我梳理领域术语" -> deep-dive 和 domain-modeling 都可能触发. deep-dive 是 domain-modeling 的**驱动者**. 分层: domain-modeling (底层写原语, model) <- deep-dive (上层访谈, user). 不是路径断裂, 是分层正确.
- F. "这个项目我想从零学起" -> codebase-onboarding. 长流程 + 空跑风险 (没 codebase 时 model 误触发) + 重产出. 维持 user.

**修正**: 无 frontmatter 修正, 理由强化 (commit-revert 从 "危险" 改 "撤销级别歧义"; codebase-onboarding 加 "空跑风险").

**好的保留**: domain-modeling model 立约 (design + 分层逻辑) 经第二轮验证仍成立.

### 第 3 轮: 触发词冲突

**真实场景**:
- G. "帮我重构跨 3 个文件" -> ACR (user) 和 writing-plans (第 1 轮改 model) description 都含 "refactor/multi-file". writing-plans auto-reach 会**绕过 ACR 前置 gate**, 违反 ACR "mandatory pre-implementation gate" 设计.
- H. "这个需求我要先想清楚" -> deep-dive ("想清楚") 和 intent-inference ("想清楚") **触发词完全重叠**. 两者都 user 时 model 不 reach 任何一个.
- I. "写个 spec" -> spec-driven-development. 正式交付物不该 auto-reach, 但 description "requirements vague" trigger 会跟 intent-inference (model) 冲突.

**修正**:
- writing-plans: **撤回第 1 轮的 model**, 恢复 user. 修 description 加 "after ACR verdict".
- intent-inference: user -> **model** (前置推断应 auto-reach). 分层: intent-inference(model) -> deep-dive(user).
- spec-driven-development: 维持 user, 修 description 去 "requirements vague" trigger.

**坏的改**: 第 1 轮 writing-plans -> model 判错, 第 3 轮撤回.

### 第 4 轮: 平衡性 + 沉淀真实性

**对照验证**:
- J. the baseline v1.1 user 数 -- 子代理 D 说 11, 子代理 B 表数出 13. **两子代理对 the baseline 计数不一致**. 裁定: the baseline 精确比例不重要, 模式重要. arthurpower 9:17 不算少, S1-S6 discipline (8 个 model) 是 the baseline 没有的差异化层.
- K. "审计这个改动" -> /audit command + arthurpower-audit-agent. command/agent 是 harness 扩展层, 不纳入 skill user/model 分类.
- L. CONTEXT.md L50 沉淀 -- 子代理 A 实测 `./skills/<bucket>/<name>` pass, 但 **arthurpower 当前平铺无 bucket 层**. Phase 1 路径应是 `./skills/<skill-name>`.

**修正**: §一§十更正补 "平铺 vs 分桶" 两种路径格式. command/agent 边界澄清.

**好的保留**: 第 3 轮 9:17 比例经 the baseline 对照验证成立.

### 第 5 轮: symlink 真实性 + 实施可行性

**真实性核实**:
- M. dispatching-parallel-agents "symlink-protected" -- 子代理 C 引用 using-agent-skills prose 警告. 但 prose 警告是**软约束**, 不是 frontmatter dmi:true. frontmatter 没 dmi = 默认 model.
- N. Phase 1 改 9 frontmatter 真实风险 -- 改 description 去 trigger 会让共享 trigger 的 skill 误伤.
- O. 最终 9 user 清单核实.

**修正**:
- dispatching-parallel-agents: 去 "symlink-protected" 矛盾标记, 明确 model-invoked.
- Phase 1 步骤 2 加 "description trigger 去重" 子步骤 (不只加 dmi).

**好的保留**: Phase 1 "先验分类 work 不动目录" 策略正确.

### 5 轮收敛最终结论

| 项 | 子代理 C | 子代理 D | 5 轮裁决后 |
|----|---------|---------|-----------|
| user 数 | 12 | 11 | **9** |
| model 数 | 14 | 15 | **17** |
| using-agent-skills | user | model | **model** (第 1 轮) |
| intent-inference | user | (未列) | **model** (第 3 轮) |
| writing-plans | user | user | **user** (第 1 轮改 model, 第 3 轮撤回) |
| domain-modeling | user | model | **model** (冲突仲裁, design 立约优先) |
| dispatching-parallel-agents | model (symlink-protected) | model | **model** (第 5 轮去矛盾标记) |

**关键**: 5 轮都基于真实 description 文本 + 真实使用场景, 不是凭概念推断. 撤回了 1 个误判 (第 1 轮 writing-plans), 保留了所有经多轮验证成立的判定.

## 3. 第 6-10 轮详记 (code-review / wayfinder 缺口, V 第二轮要求追加)

### 第 6 轮: code-review 缺口

**真实场景**: ACR 是改前 gate (5 verdict: S1-S6 + 任务分解), the baseline code-review 是改后审查 (标准维度 + 规范维度 + Fowler smell). 两者维度完全不同.

**4 选项**:
- A: v0.7.0 新增 code-review skill (扩 scope 风险高)
- B: 蒸馏到 ACR (改前 ≠ 改后, 概念错位)
- C: v0.7.0 不动, v0.8.0 新增 (S6 最小变更)
- D: 蒸馏到 writing-plans (writing-plans 已膨胀)

**第 6 轮裁决**: **C + 部分 B** -- v0.7.0 不新增, 集成现有 v-code-review CLI + writing-plans acceptance 加引用. (**第 11-14 轮被 V 反馈后撤回**)

### 第 7 轮: wayfinder 缺口

**真实场景**: writing-plans 假设方向已定, ACR 假设 5 维度可判定, session-handoff 只压缩交接. scope 未定 + 多 session + 方向不明的大型规划, 无 skill 覆盖. 三者拼不出 wayfinder.

**4 选项**:
- A: v0.7.0 新增 wayfinder skill (依赖 GitHub Issues, scope 大)
- B: 蒸馏到 writing-plans (writing-plans 已膨胀, 跟 "AFTER ACR verdict" when-to-use 冲突)
- C: 蒸馏到 using-agent-skills router (规模路由分支, 不新增 skill)
- D: 不补 (V 明确关注, 不可)

**裁决**: **C + B 部分** -- v0.7.0 不新增 wayfinder skill, router 增设规模路由分支 + writing-plans 加 scope-unclear 指引 + 引入 decision ticket 概念. (**V 字面采纳**)

### 第 8 轮: 跟前面 5 轮的冲突复查

**结论**: 无冲突. code-review/wayfinder 是新 skill, 不在 9 user 列表; 即使 v0.8.0 新增, 按 "前置 router 类 model" + "改后审查 user" 分层即可.

**关键**: 第 6-7 轮都收敛到同一原则 -- v0.7.0 最小变更 (不新增 skill) + v0.8.0 再补. **这个收敛是真实的, 不是凑的.**

### 第 9 轮: Fowler smell 落点

**真实场景**: 第 6 轮提 "ACR verification 加 v-code-review 触发", 但 Fowler smell 是改后审查, ACR 是改前 gate. 两者**不同时点**, 不能混.

**裁决**:
- **不改 ACR** (改前 gate 不该有 smell 检查)
- v-code-review SKILL.md (user-level) 加 Fowler smell baseline 段 (~12 项)
- writing-plans Acceptance 加 "每 task 完成后用 v-code-review 跑双维度审查, verdict yes 才能 commit"
- ACR Verification 加 "Plan 包含 v-code-review 触发规则" (触发规则, 不是 smell 检查本身)

**好的保留**: ACR 5-verdict frame 不动.

### 第 10 轮: 收敛 (后续被 11-14 轮修正)

注: 第 10 轮的 "v0.7.0 不新增 code-review skill + 塞 writing-plans" 结论, 在 V 第二轮反馈后被第 11-14 轮**撤回**. 见下.

## 4. 第 11-14 轮详记 (V 反馈: code-review 重叠技能冲突)

### V 反馈原文

> "Wayfinder 方案采纳, 但是 code review 那个需要我们暂时来探讨一下, 因为那个是一个独立的智能体 CLI, 跟派发子代理有点不同. 我建议还是不要融到这个技能里面, 可以融到别的技能里面. 比如说, 我之前有的 code quality, 还有其他的重叠文件, 这个时候就体现到你决策的意义了. 之前的派发逻辑和代码审查的派发子代理相关技能, 可能描述和技能体现决策位置中有冲突或决策失误, 需要你现在来找出来."

### 第 11 轮: 5 个冲突/失误盘点 (V 让我找的)

| # | 冲突/失误 | 涉及资产 |
|---|----------|---------|
| 1 | **悬空依赖** | `code-reviewer` agent L12 引用 `code-review-and-quality` skill, 该 skill 不存在 |
| 2 | **三体 S1-S6 重复** | arthurpower-audit-agent (改后) + maintainability-reviewer (改后第三段) + architecture-change-reviewer skill (改前) 都审 S1-S6 |
| 3 | **dispatcher 派 code-reviewer 撞 prose** | code-reviewer L67 "Do not invoke from another persona" vs arthurpower-dispatcher 派 fanout |
| 4 | **v-code-review description 跟 audit-agent trigger 重叠** | v-code-review "审查/审 PR" vs arthurpower-audit-agent "审计/审查/S1-S6" |
| 5 | **我的决策失误 (V 指正)** | 第 6/9 轮把 v-code-review 塞 writing-plans/ACR (时点错位) |

### 第 12 轮: v-code-review 落点重新裁决

**V 约束**: v-code-review 是独立智能体 CLI, 不融 writing-plans.

**4 选项评估**:
- A: 融 ACR (改前, 时点错位) ✗
- B: 融 arthurpower-audit-agent (agent 不是 skill) ✗
- C: 新建 arthurpower:code-review skill (承载 v-code-review CLI 集成规约 + 双维度 + Fowler smell) ✓
- D: 不改 (V 问"决策意义"暗示要融) ✗

**裁决**: **C - 新建 arthurpower:code-review skill** (v0.7.0 一次性立好, 不经 v0.9.0). skill body 含 v-code-review CLI 调用规约 + 双维度 + Fowler smell 12 项 + verdict 解析 + 三体 S1-S6 决策位置注释.

### 第 13 轮: 三体 S1-S6 重叠 + dispatcher 误用 + trigger 去重

**冲突 2 解决** (三体 S1-S6):
- ACR (skill, 改前 plan) -> 5 verdict: 不动
- arthurpower-audit-agent (agent, 改后 S1-S6, 限 arthurpower 自身) -> 不动
- maintainability-reviewer (user agent, pre-merge 第三段 S1-S6, 通用项目) -> 不动
- **明确分工**: audit-agent 审 plugin 自身改动; maintainability-reviewer 审被审项目代码; ACR 是改前 plan gate.

**冲突 3 解决** (dispatcher 派 code-reviewer):
- code-reviewer L67 "Do not invoke from another persona" 是自约束
- **dispatcher 不派 code-reviewer**, 派 quick-reviewer (轻量) 或直接调 v-code-review CLI (不派 agent)
- code-reviewer 留给 `/review` slash command 单独触发

**冲突 4 解决** (trigger 重叠):
- v-code-review = 通用 Git 改动审查 (不限 arthurpower)
- arthurpower-audit-agent = arthurpower 自身 S1-S6 审计
- description 作用域去重: v-code-review 加 "通用项目, not limited to arthurpower"; audit-agent 加 "限 arthurpower 自身改动"

### 第 14 轮: 收敛最终路径 (10 轮 + 4 轮 = 14 轮)

| 项 | 前面 10 轮 | 第 11-14 轮修正 | 最终路径 |

## 6. 关键裁定 (3 个高优先级)

### 6.1 plugin.json skills 字段路径格式 (实测裁定)

**争议**: CONTEXT.md L50 沉淀 "schema 不接受字符串数组" vs the baseline ADR 0002 "接受路径数组".

**裁定** (子代理 A 实测):
- 合法: `./skills/<skill-name>` (平铺) 或 `./skills/<bucket>/<name>` (分桶)
- 不合法: 裸 skill 名 / 不含 `./` 的路径
- 删除该字段后 framework 回退目录扫描也 work

### 6.2 domain-modeling 加载方式 (冲突仲裁)

**争议**: 子代理 C (user-invoked) vs 子代理 D (model-invoked) vs design 立约 (model).

**裁定**: **model-invoked**. 理由:
1. context-loop-refactor.md L17 D2 立约
2. 写主权靠 hook + discipline 三层保证
3. 跟 the baseline 对齐

### 6.3 三体 S1-S6 决策位置分工 (V 让找的冲突)

| 资产 | 时点 | 触发 | 作用域 |
|------|------|------|--------|
| architecture-change-reviewer (arthurpower skill) | 改前 | plan | arthurpower |
| arthurpower:code-review (arthurpower skill, v0.7.0 新建) | 改后预 commit | "审代码" | 通用 |
| arthurpower-audit-agent (arthurpower agent) | 改后预 commit | "audit/S1-S6" | arthurpower 自身 |
| maintainability-reviewer (user agent) | pre-merge 第三段 | spec+code quality 过门后 | 通用项目 |
